## Контекст, который важно знать сразу

- **Сегодняшняя дата важнее даты в документах.** `docs/SHEKARA.md` писался 3 октября 2026 и
  весь план по дням (разделы 4.5а/4.5б) расписан от этой даты. **Сверь с реальной сегодняшней
  датой** и, если прошло больше пары дней, пересчитай план: подача в Оргкомитет — **20 октября
  2026**, заморозка кода — за 5 дней до внутреннего срока вуза (правило в 4.5в), финал — 10 или
  13 ноября 2026. Не следуй датам из 4.5а/4.5б буквально, если они уже в прошлом.
- **Состав:** 1–2 человека, студенты, своей командой вчетвером (как в первом черновике KARAVAN)
  это не делается — тот вариант отклонён.
- **Почему именно ШЕКАРА, а не KARAVAN.** Это был уже второй прогон арены (100-агентного
  турнира). Первый дал KARAVAN (неттинг-движок для банковской группы) — он не проходил по
  реальному регламенту конкурса АБРК (нужна команда из 4, 48 часов, нет данных банковской
  группы у студента). Второй прогон на реальных правилах конкурса (жюри: банки, НБК, АБР, ЕБРР,
  МФЦА, эксперты AI/кибербез; 1–2 автора; AI-треки в игре) выбрал ШЕКАРА и в финальной проверке
  победил старый вариант 81:42. Решение собрано из 32 конкурентов за 5 раундов атак/защиты.
- **Среда (Windows):** `python3`/`python` могут не работать (заглушки Microsoft Store) — вызывай
  `py`. `gh` CLI не установлен — репозиторий на GitHub создавался вручную через веб. Доступа к
  Kaggle у Claude нет: датасет AMLworld может скачать только человек через `kaggle.json`
  (инструкция в README.md).
- **Репозиторий:** https://github.com/Falconwu17/shekara — уже запушен коммит с README,
  `.gitignore`, `docs/SHEKARA.md`. Работай строго в одной локальной копии (`D:\shekara`), не
  плоди дублей клона — уже была путаница с `C:\Users\Сагир\shekara`.

## Что уже сделано (сессия 10 октября)

Всё ниже покрыто тестами: `py -m pytest` → 59 тестов, все проходят.

**Протокол (`protocol/`)**
- [x] `matching.py` — `tx_ref` = SHA-256 полей перевода + счётчик дублей `k` (3.5).
- [x] `tokens.py` — HMAC пары банков: `tx_ref_hmac` и псевдоним счёта.
- [x] `accountant.py` — ε за 30 дней по формуле таблицы 3.4 (c + 2√(c·ln 1/δ), c = k/2z²),
  журнал выпусков по счетам. Opacus не используется: формула совпадает с таблицей, Opacus даст
  чуть меньший ε — можно подключить к финалу.
- [x] `gateway.py` — шлюз банка (чистая логика, без FastAPI): need-to-know (только зачисленный,
  не старше 30 дней, одинаковый `not_found`), квота `int(1,2·n) + 50` на пару в сутки
  (считается **до** поиска), L1/L2/L3 (int8 для L2 — шкала [−4; 4], выбрана нами), суточный
  кэш, ночная рассылка по последнему переводу (квоту не тратит), приём чужих выпусков у
  внешних узлов, поиск исходящих в окне.
- [x] `hub.py` — журнал аудита в SQLite с хэш-цепочкой SHA-256 (`head`, `verify`), маршрутизация
  запросов, рассылки и шагов инцидентов; в журнале только метаданные, без сумм.

**Инциденты и очередь**
- [x] `trace/incident.py` — режимы I0/I1/I2, квота мягких инцидентов 0,02% активных счетов,
  шаг между банками несёт только ссылку, тип и номер шага; пересылка по уже зачисленным
  исходящим в окне Δt = 60 мин; свой сегмент без чужих звеньев; `Operator` собирает дерево
  цепочки (по мягкому — только число звеньев), доступ только для роли «оператор».
- [x] `online/alerts.py` — очередь алертов с суточным бюджетом (0,1% активных счетов): входящий
  инцидент не ставит счёт сверх бюджета.

**Данные (написаны и проверены на синтетике в формате HI-Small, `tests/synth_amlworld.py`)**
- [x] `data/amlworld.py` — загрузка CSV (поля строками, `row_no` = номер строки файла),
  разбор `HI-Small_Patterns.txt`, `align_patterns` — сопоставление строк паттернов с переводами
  (нормализует ведущие нули в номерах банков и запись сумм).
- [x] `data/stats.py` (`make stats`) — подневная таблица, полные дни и хвост, разбиение 60/10/30,
  выбор N по правилу 3.3 только на днях обучения (тест проверяет, что метки теста не влияют),
  `split_decision.json` не перезаписывается без `--force`; отчёт `experiments/results/stats.json`:
  4 цифры 2.2, дубли строк, транзитные счета по частям, объём ночной рассылки по парам.
- [x] `data/split.py` (`make data`) — DuckDB-база на банка-участника (только свои строки, без
  колонки ключа, с `row_no`), `data/processed/full_days.parquet` для оракула, `load_bank_keys`
  для шлюза. Тест: два банка из своих баз считают одинаковый `tx_ref`.
- [x] `data/labels.py` — «транзитный счёт» и грубая метка; `data/channel_map.py`.
- [x] `demo/pick_case.py` (`make case`) — три уровня правил выбора демо-паттерна, без баллов.
- [x] Скорость: на синтетике 1,2 млн строк `stats` ≈ 1 с, `split` ≈ 5 с.

**Окружение:** установлены `pytest numpy polars duckdb pyarrow` (Python 3.13, через `py`).

## Итоги `make stats` на настоящем HI-Small (10 октября)

- 5 078 345 переводов, 30 528 банков; все 3 209 строк паттернов (370 паттернов) сопоставлены.
- Полных дней 10, хвост 8 дней (≈ 60% отмывания) отброшен. Обучение 1–6.09, валидация 7.09,
  тест 8–10.09.
- **N = 30** — порог 150 ожидаемых положительных рёбер между участниками в тесте не достигнут
  ни при каком N (при N = 30 ≈ 70), поэтому по правилу 3.3 основной тест значимости — парный
  бутстреп по паттернам. Сюжет питча «пять банков» не проходит → «30 банков-участников».
- Цифры 2.2 (дни обучения, AMLworld): 98% переводов отмывания межбанковские; один банк видит
  ≈ 28% паттерна; в 82% паттернов счета были в межбанковских переводах раньше; интервал
  вход → выход на транзитном счёте: медиана ≈ 21 ч, p10 ≈ 2 ч, p90 ≈ 66 ч. → в питч идёт
  удержание в «сжатом времени» (3.6), во времени AMLworld оно будет завышено.
- Демо-паттерн: **235 (SCATTER-GATHER)**, 16 переводов, 3 банка-участника, начало 8.09 01:11.
  Правило уровней 1–2 дополнено условием «≥ 2 / ≥ 1 перевода между участниками» до обучения
  (см. 4.1 в docs/SHEKARA.md).
- `split_decision.json` и правила `pick_case.py` закоммичены до первого чекпойнта модели.
